# Fairshare domain

Pure, immutable aggregate transitions. No network calls, AI money arithmetic, or payout submission. Explicit enums; USD MVP; exact integer cents and basis points. All human proposals stay inactive until every participant approves the same version. Final approval activates the version when its advance is already confirmed; an unconfirmed advance leaves the approved version awaiting organizer confirmation, which may activate it. Source excerpts must be verified by the extraction/application layer; this module validates their presence, not legal accuracy.

## API integration requirements

- Load and persist an entire transition in a serialized DB transaction with optimistic revision checks. A read/modify/write without transaction is unsafe.
- Authenticate actors at the server. Never accept actor IDs from arbitrary browser payloads. This module checks membership/organizer role, not identity proof.
- Only call `allocateConfirmedRevenue` after verifying PayPal payment/capture/reference/currency/amount and actual processing fee. Missing fee data must BLOCK allocation, not default to zero.
- Enforce globally unique provider capture IDs across collaborations, not only within this aggregate. Store verified webhook event IDs durably and reconcile duplicate delivery safely.
- `grossCents - feeCents` is conserved. Recoupment and residual shares are BOTH included in allocation totals. Recoupment progress carries across versions referencing the same immutable advance ID.
- Preview returns `previewOnly: true`, does not record revenue, and never sends money. Unresolved assumptions remain marked.
- ALLOCATED does not mean paid. Actual payouts, payout fees, recipient verification and provider outcomes belong to payment/application layers. No routine re-approval of calculated shares is required by this domain; payout authority and safety checks remain separate.
- Refunds (`applyCaptureRefund`) come back out of the payment they refund, recomputed from that payment's stored allocation, never the current rules. **Ordering decision:** a refund is undone in the reverse of how the payment came in. The payment first paid back the advance, so the refund first reduces what this payment paid back (the advance counts as less paid back and later payments repay it again); the rest comes off each person's split in proportion to what they still get from that payment, by largest remainder. Integer cents, never negative; refunds on one payment cannot add up to more than it.
- Fees on refunds: the reversal uses PayPal's net refund. BEFORE_SPLIT takes the net refund off everyone, so an unreturned fee is shared by the split. ORGANIZER_SHARE takes the refund off gross shares and gives only a returned fee back to whoever covered it. An unreturned fee bigger than what the payment has left becomes a shortfall owed by the same people.
- A refund that reconciles cleanly before any payout from that payment changes only that payment. The agreement pauses (`reviewHold`) after payouts started, for a reversal, when something becomes owed, or when the advance was replaced since the payment. Each person's overpayment is recorded in `owedBack`. A replayed refund ID is a no-op.
- `resumePayouts` (organizer) clears the pause. Each refund-created liability is stored with its capture, refund, person and kind. Future-payment offsets and credits reference those exact liabilities, so a fee return, refunded offset payment or returned payout changes only the recovery that caused it. `owedBack`, `offsetRecovered`, `creditBack` and `externallySettledOverpayments` remain compatibility views of this source-specific ledger. With `offsetFromFuturePayouts`, the balance is kept back from that person's next shares (`offsetCents`); otherwise the remaining liability is recorded as settled outside Fairshare. If PayPal later confirms that payout was not delivered, the attributed recovery produces one ledger credit on the person's next share. The application layer must refuse while a dispute or provider event is unsettled.
- Historical rows remain readable. If a row predates `refundAttributionVersion: 1` and contains refund liability, offset, credit or external-settlement evidence, a new money transition fails with `ATTRIBUTION_REQUIRED`; the domain will not infer which capture supplied or consumed a generic balance. An operator must reconstruct the exact liability lots and allocation references from durable provider and payout evidence before resuming money movement.
- Other reversals and disputes hold all allocations in the affected collaboration, preserving historical amounts/recoupment. Unknown captures must remain in an unmatched-event queue.
- Data is local aggregate state, not a legal contract execution/signature system. Historical source docs must be versioned/immutable. Participant changes, FX, taxes and multiple simultaneous advances are outside this MVP.

## Supported fee policies

BEFORE_SPLIT deducts actual processing fees before recoupment/residual sharing. ORGANIZER_SHARE calculates gross entitlements then charges the designated organizer's allocation; if insufficient, fails with FEE_EXCEEDS_SHARE rather than creating negative balances.

Rounding uses largest remainders with stable user-ID tie breaking. Every approved rule must specify participant shares summing to 10,000 basis points.
